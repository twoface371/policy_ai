# AI 법·정책 동향 분석 플랫폼

법제처 국가법령정보 OpenAPI 기반. 사보원 감시 대상 법령 **107건**의 개정을 **자동으로** 추적·분석한다.

**PostgreSQL 전용 · 자동 적재 · 조회/다운로드 + 관리 화면**

---

## 동작 방식

```
서버 시작        →  미적재 법령의 전문을 자동 수집
                 →  오늘 점검 이력이 없으면 즉시 판본 대조 1회 (따라잡기)
매일 지정 시각   →  판본 대조 → 바뀐 법만 전문 갱신 → 감지분 자동 분석
사용자           →  개정사항 조회 · 리포트 다운로드 · 문서 검사 · 목록/설정 관리
```

수동 적재 버튼도, 메일 발송도 없다. 수집·분석은 서버가 알아서 하고 사용자는 결과를 본다.

감시 법령 추가·삭제, 전문 삭제, API 키 설정, 문서 저촉 검사는 **화면에서** 할 수 있다.
`config.json`을 직접 편집해도 되지만, 그 경우 서버를 재시작해야 반영된다.

### 개정을 어떻게 감지하는가

감시 법령의 **현재 판본번호를 법제처에서 받아 DB와 대조**한다. 번호가 그대로면 아무 일도
하지 않고, 바뀐 것만 전문을 새로 받아 조·항·호·목으로 쪼개 저장한다. 이전 판본과
`body_hash`를 비교해 **바뀐 조항만** 골라 분석에 넘긴다.

- **멱등하다.** 하루에 여러 번 돌려도 무해하고, 며칠 걸렀다가 켜도 밀린 개정을 한 번에
  따라잡는다. 맥이 잠자기로 들어가 타이머를 놓치는 로컬 환경을 전제한 설계다.
- **분리시행은 별도 큐로 잡는다.** 부칙에 "제N조는 YYYY.M.D부터 시행"으로 적힌 조항은
  시행일이 와도 판본번호가 바뀌지 않는다. 적재할 때 `pending_enforcement`에 넣어 두고
  날짜가 도래하면 판본번호와 무관하게 다시 받는다.
- 점검 결과는 `check_log`에 남는다. "개정이 0건이라 조용한 것"과 "API가 죽어서 조용한 것"을
  구분하기 위한 것이다.

> 신구법 대비표(`oldAndNew`) API를 쓰던 옛 경로가 `core.py`에 남아 있지만
> **현재 흐름에서는 호출되지 않는다.** `law_changes`의 `trigger_type='legacy'` 행이 그 경로의
> 산물이다. 지금 감지되는 개정은 `mst`(판본 대조) 또는 `pending`(분리시행)으로 기록된다.

## 1. 사전 준비

### PostgreSQL

서버가 떠 있어야 한다. 데이터베이스는 **직접 만들 필요 없다** — 첫 실행 때
`postgres` DB에 붙어 없으면 만든다.

```bash
brew install postgresql@17
brew services start postgresql@17
```

Homebrew로 깔면 macOS 계정과 같은 이름의 슈퍼유저가 만들어지고 로컬 접속은
비밀번호가 필요 없다. `config.json`의 `db.user`를 그 계정으로 두면 된다.

전용 계정을 쓰는 것을 권장한다(운영 시 필수).

```sql
CREATE USER policy_ai WITH PASSWORD '비밀번호';
CREATE DATABASE policy_ai OWNER policy_ai;
```

### 파이썬 패키지

```bash
pip install fastapi uvicorn httpx openai asyncpg python-multipart
```

`python-multipart`는 **문서 검사** 탭(파일 업로드)에 필요하다. 없으면 서버 기동은 되지만
`/api/check-document`가 500으로 떨어진다.

문서 검사에서 읽을 파일 형식에 따라 추가로 설치한다. `.txt`만 쓸 거면 필요 없다.

```bash
pip install python-docx pdfplumber pyhwp   # docx / pdf / hwp
```

검사 결과를 **PDF로 내려받으려면** `reportlab`, **엑셀 양식**을 쓰려면
`openpyxl`이 필요하다. 마크다운 다운로드는 추가 설치 없이 된다.

```bash
pip install reportlab openpyxl
```

> PDF는 맥에 기본 탑재된 `/System/Library/Fonts/Supplemental/AppleGothic.ttf`를
> 임베드한다. 이 글꼴이 없는 환경(리눅스 서버 등)에서는 PDF 다운로드만 실패하고
> 나머지 기능은 그대로 동작한다. 옮길 계획이 있으면 글꼴 파일을 함께 두고
> `report.py`의 `FONT_PATH`를 고치면 된다.

### 법제처 인증키

[open.law.go.kr](https://open.law.go.kr) 가입 후 발급받아 `config.json`의 `law_api_key`에 넣는다.

## 2. 설정 — `config.json`

```json
{
  "law_api_key": "발급받은키",
  "llm": {
    "enabled": true,
    "api_key": "sk-...",
    "model": "gpt-4o-mini",
    "base_url": "",
    "max_input_chars": 20000,
    "max_tokens": 2500
  },
  "db": {
    "host": "127.0.0.1", "port": 5432,
    "user": "postgres", "password": "", "name": "policy_ai"
  },
  "collect": { "max_analyze": 20 },
  "auto": { "init_on_startup": true, "daily_check": true, "daily_time": "22:00" }
}
```

| 키 | 의미 |
|---|---|
| `llm.enabled` | `false`면 AI를 쓰지 않고 규칙 기반으로만 판정 (과금 없음) |
| `llm.base_url` | Qwen 등 OpenAI 호환 서버 주소. 비우면 OpenAI |
| `llm.max_input_chars` | 조문 입력 상한(기본 20000). 넘으면 앞에서 자르지 않고 **조문 단위로 선별**하며, 분석 범위가 `선별 분석`으로 표시된다 |
| `llm.max_tokens` | 응답 토큰 상한 |
| `collect.max_analyze` | 자동 분석 1회당 최대 건수 (과금 상한) |
| `auto.init_on_startup` | 서버 시작 시 미적재분 자동 수집 |
| `auto.daily_check` | 매일 개정 확인 자동 실행 |
| `auto.daily_time` | 실행 시각 `HH:MM` (기본 `22:00`) |

> `collect.lookback_days`와 `collect.date_mode`는 없어졌다. 판본 대조가 밀린 것을 알아서
> 따라잡으므로 조회 기간을 지정할 이유가 없고, 조회는 시행일 기준으로 통일했다.
> 설정 파일에 남아 있어도 무시된다.

`auto.daily_time`은 **설정** 탭에서도 바꿀 수 있다. 화면에서 바꾸면 다음 회차부터 반영된다
(스케줄러가 매 회차마다 설정을 다시 읽는다).

### 비밀값은 환경변수로 뺄 수 있다

설정 파일에 키를 남기고 싶지 않으면 환경변수가 우선한다.

```bash
export LAW_API_KEY=...
export OPENAI_API_KEY=...
export PGPASSWORD=...
```

## 3. 실행

```bash
python app.py
```

- 화면: http://127.0.0.1:8000
- API 문서(자동 생성): http://127.0.0.1:8000/docs

개발 중 자동 리로드가 필요하면:

```bash
uvicorn app:api --reload --port 8000
```

종료는 **`Ctrl+C`**. 창을 그냥 닫으면 프로세스가 남아 다음 실행 때 `address already in use`가 난다. 그때는:

```bash
lsof -ti:8000 | xargs kill
```

### 첫 실행 때 일어나는 일

```
① 데이터베이스 policy_ai 자동 생성
② 테이블 9개 생성
③ 감시 법령 107건 자동 등록
④ 1초 뒤 전문 자동 수집 시작 (법제처 API 200회 남짓, 수 분 소요)
⑤ 오늘 점검 이력이 없으므로 판본 대조 1회 실행
⑥ 이후 매일 auto.daily_time(기본 22:00)에 개정 확인 대기
```

수집이 끝날 때까지 화면의 통계는 비어 있다. 진행 상황은 아래 4번을 참고.

## 4. 화면

탭 6개다.

| 탭 | 내용 |
|---|---|
| **현황** | 통계, 자동 적재 상태, **지금 개정 확인** 버튼 |
| **개정사항** | 기간·키워드 검색 → 상세에서 개정 전/후 조문과 AI 판정 확인. 개정 건별 개별 리포트 다운로드 |
| **법령 전문** | 수집된 법령 전문 검색·열람. 목록에 **변경 배지**, 상세에서 **판본 비교**·전문 삭제 |
| **감시 법령** | 목록·수집 상태 + 추가·삭제 |
| **문서 검사** | 문서 또는 **엑셀 양식** 업로드 → 인용 법령·조를 현행과 대조. 결과 저장·다운로드(md/pdf) |
| **설정** | 법제처·AI 키, 모델, 개정 확인 시각. 규칙기반 결과의 AI 재분석 |

### 문서 검사 — 두 가지 입력

**자유 문서**(hwp/hwpx/pdf/docx/txt)를 올리면 정규식으로 인용을 뽑는다. 편하지만
법령명의 경계를 추측해야 해서 완벽하지 않다(실측 재현율: 첫 후보 84%, 후보를
법제처에 조회해 보정하면 100%).

**엑셀 양식**(xlsx/csv)에 법령·조를 직접 적어 올리면 추측이 사라진다. 화면의
`양식 내려받기`로 빈 양식을 받아 채우면 된다. 인용이 많거나 서식이 복잡한
문서라면 이쪽이 낫다.

```
법령명 | 조 | 항 | 비고
개인정보 보호법 | 제15조 | 1 |
지능정보화 기본법 | 46조의2 | | 가지번호는 이렇게
```

조는 `제15조`·`15조`·`15` 아무 형식이나 되고, 항은 비워도 된다(**판정은 조 단위**,
항은 표시용). 읽지 못한 줄은 버리지 않고 결과에 **양식 오류**로 함께 보여 준다.

### 개정 판정 기준

`기준일`을 넣으면 그날 시행 중이던 판본과 현행을 조문 단위로 대조한다. 비우면
현행 바로 앞 판본과 대조하므로 **가장 최근 시행된 개정만** 보인다. 오래된 문서를
검사할 때는 작성 시점을 기준일로 넣어야 그 사이 변화가 전부 잡힌다.

판정은 `변경 없음 / 개정됨 / 신설 / 삭제 / 조항 없음`이며, 바뀐 조는 기준일 시점과
현행의 조문을 나란히 보여 준다. 삭제된 조는 법제처가 `제46조 삭제 <2025.1.21>`
껍데기로 남기므로 그것도 삭제로 잡는다.

### 판본 비교 (변경분 색칠)

법령 전문 → **전문** → **판본 비교**. 이전 판본과 조문 단위로 대조해
**추가는 초록, 삭제는 빨강 취소선**으로 표시하고 추가/삭제/변경 조항 수를 함께 낸다.

신구법 대비표 API를 쓰지 않고 **DB에 적재된 조항호목을 직접 대조**한다.
두 판본의 `(조문 좌표, body_hash)` 시퀀스를 정렬해 짝을 맞추고, 내용이 바뀐 조항만
문자 단위로 다시 비교한다. 항이 중간에 신설돼 뒤 번호가 밀려도 밀린 항 전부가 아니라
**실제로 신설된 항 하나만** 추가로 잡힌다.

> 법제처가 항번호를 주지 않는 조문이 있어, 그런 조문은 표기가 `제2조제17항`이 아니라
> `제2조`로 뭉뚱그려진다. 대조 결과 자체는 영향받지 않지만 화면에 경고가 뜬다.

> 판본은 개정이 감지될 때마다 쌓인다. 처음 수집한 법령은 판본이 하나뿐이라
> 비교 대상이 없고, 목록의 변경 배지도 `-`로 나온다. 개정이 감지되면 채워진다.

### 수동 개정 확인 — 개발 중 데이터 쌓기

**현황** 탭의 **지금 개정 확인** 버튼. 스케줄러(기본 22:00)를 기다리지 않고 판본 대조를
지금 한 번 돌린다. 매일 도는 것과 **완전히 같은 경로**다.

감시 법령 전체를 훑으므로 107건 기준 **1~2분** 걸린다. 서버가 백그라운드로 돌리고 화면은
진행 상황(`판본 대조 · 법령명 (60/107)`)과 로그를 2초마다 폴링한다. 끝나면 대상/개정/
변화없음/실패 건수가 뜬다.

판본 대조는 멱등이라 여러 번 눌러도 무해하다. 이미 실행 중이면 `409`로 막힌다.

### 진행 상황을 자세히 볼 때

```bash
curl http://127.0.0.1:8000/api/collect/status
```

`phase`(현재 처리 중인 법령), `done`/`total`, `result`(점검 요약), 최근 로그 200줄이 나온다.
실패한 법령의 사유는 `result.detail`에 들어 있다.

## 5. 감시 법령 상태

| 표시 | 뜻 | 조치 |
|---|---|---|
| **적재됨** | 전문 정상 저장 | — |
| **미적재** | 아직 수집 안 됨 | 서버 재시작하면 자동 수집 |
| **검색안됨** | 법령명으로 법제처에서 못 찾음 | 명칭 확인 필요 (아래 참고) |
| **본문없음** | 검색은 됐으나 조문 파싱 실패 | 원문 구조 확인 필요 |

시작 시 자동 적재는 **"적재됨"이 아닌 항목만** 재시도한다. 명칭을 고친 뒤 서버를 재시작하면
해당 항목만 다시 받는다.

> ⚠️ **이 상태 표시는 서버 시작 시 자동 적재에서만 갱신된다.** 매일 도는 판본 대조도 신규
> 법령의 전문을 수집하지만(`save_version`이 `law_fulltext`도 함께 갱신한다) 감시 목록의
> `status`는 건드리지 않는다. 그래서 화면에서 법령을 추가하면, 전문이 이미 들어온 뒤에도
> 서버를 재시작하기 전까지 **미적재**로 표시될 수 있다. 실제 수집 여부는 **법령 전문** 탭에서
> 확인한다.

### "검색안됨"이 뜨는 경우

사보원 목록의 이름과 법제처 정식 명칭이 다를 때 발생한다. `core.py`의 `SEARCH_ALIAS`에 한 줄 추가하면 된다.

```python
SEARCH_ALIAS = {
    "정보보호시스템 평가·인증 지침": "정보보호시스템 평가·인증 등에 관한 고시",
    ...
}
```

화면 이름은 그대로 두고 **검색만 정식 명칭으로** 나간다. 정식 명칭은 [law.go.kr](https://www.law.go.kr)에서 확인한다.

폐지된 규칙이라 법제처에 아예 없는 경우도 있다. 그때는 **감시 법령** 탭에서 해당 항목을
삭제한다(기본 목록 자체에서 빼려면 `DEFAULT_WATCHLIST`에서도 줄을 지운다).

## 6. 감시 법령 추가·삭제

**감시 법령** 탭에서 추가·삭제한다. 추가한 법령의 전문은 다음 판본 대조(매일 지정 시각) 또는
서버 재시작 때 수집된다. 검색이 안 되면(`검색안됨`) 삭제하고 정식 명칭으로 다시 추가한다.

새로 추가한 법령은 비교할 이전 판본이 없으므로, 첫 수집이 **개정사항** 탭에 `비교 대상 없음`
표시와 함께 1건 올라온다. 실제 개정이 아니라 최초 적재라는 뜻이다.

기본 목록을 통째로 바꾸려면 `core.py`의 `DEFAULT_WATCHLIST`를 편집한다.

```python
DEFAULT_WATCHLIST = [
    ('전자정부법', '행안부', '법령'),
    #  법령명,      소관부처,  구분
]
```

`구분`은 **`행정규칙`이면 고시·훈령 API**를, 그 외(`법령`/`정보시스템 운영`)는 법령 API를 탄다. 잘못 넣으면 검색이 안 된다.

> ⚠️ 편집 후 서버를 재시작해도 **기존 DB에는 반영되지 않는다.** 자동 등록은 `watchlist` 표가 비어 있을 때만 동작한다. 목록을 바꿨다면 표를 비우고 재시작한다.
>
> ```sql
> TRUNCATE TABLE watchlist RESTART IDENTITY;
> ```
>
> `RESTART IDENTITY`가 없으면 id 시퀀스가 이어져 올라간다(MySQL의 TRUNCATE는
> 자동으로 되돌렸다).

현재 구성: 법령 27 · 행정규칙 28 · 정보시스템 운영 52 = **107건**

## 7. 파일 구조

```
core.py              수집 / 저장 / 분석 / 리포트 / 판본 비교  (웹 코드 없음)
law_parser.py        조항호목 파서 (DB 미접촉 순수 함수)
analyzer.py          문서 텍스트 추출 + 법령 인용 탐지 (정규식, AI 미사용)
checker.py           인용 법령을 법제처 현행법과 대조
app.py               FastAPI 라우트 + 자동 적재 스케줄러
static/index.html    화면 (빌드 도구 불필요)
config.json          설정 (API 키·DB 비밀번호 포함 · 0600)
REFACTOR_DESIGN.md   판본·조항호목 구조의 설계 근거와 법제처 API 실측 기록
raw/                 법제처 응답 스냅샷 (파서 개선 시 재파싱용)
reports/             생성된 리포트
reports/_debug/      법제처 응답 원문 (최근 30개만 보관)
```

`raw/{law_id}/{version_key}.json.gz`에 법제처 원본 응답이 남는다. 파서를 고쳤을 때
법제처를 다시 호출하지 않고 `law_articles`를 재생성할 수 있게 하려는 것이다.
그래서 **전문을 삭제해도 `raw/`는 지우지 않는다.**

`analyzer.py`는 단독 실행된다. 인용 탐지만 확인하려면:

```bash
python analyzer.py --selftest
```

## 8. DB 구조 — 테이블 9개

| 테이블 | 저장 내용 | 키 설계 |
|---|---|---|
| `watchlist` | 감시 법령과 수집 상태 | `name` 유니크 |
| `law_fulltext` | 법령 전문 텍스트 (최신 1건) | `law_id` PK — 항상 최신만 유지 |
| `law_versions` | 판본 레지스트리 (개정될 때마다 누적) | `(law_id, version_key)` PK |
| `law_articles` | 조·항·호·목 노드 + `body_hash` | `(law_id, version_key, seq)` 유니크 |
| `law_addenda` | 부칙 — 판본이 아니라 **법령**에 종속되고 누적된다 | `(law_id, 공포일자, 공포번호)` 유니크 |
| `pending_enforcement` | 분리시행 대기 큐 | `(law_id, 시행일, source_version)` 유니크 |
| `law_changes` | 개정 이력 | `mst` PK |
| `analyses` | 분석 결과 | `(mst, content_hash)` PK |
| `check_log` | 일일 점검 이력 (성공/실패·건수) | `id` |

`law_articles`의 유니크 키는 조문 좌표가 아니라 `seq`에 걸려 있다. 파서가 좌표를 잘못 뽑아도
적재 자체는 실패하지 않게 하는 안전장치다. 대신 좌표가 겹치면 판본 비교가 부정확해지므로,
그 경우 화면에 경고를 띄운다.

`law_versions.version_key`는 **전문 조회의 법령일련번호**이고, `law_changes.mst`와는 다른
값이다(후자는 신구법일련번호에서 온 이름). 판본 대조로 감지된 개정은 `mst`에 새 
`version_key`가, 분리시행으로 감지된 것은 `{version_key}@{시행일}`이 들어간다.

`content_hash`는 **개정 전/후 조문 + 부칙 + 프롬프트 버전 + 모델명**의 해시다. 입력이 그대로면
재분석하지 않고, 조문이 바뀌거나 프롬프트·모델을 바꾸면 자동으로 다시 분석한다. 모델명과
프롬프트 버전까지 키에 넣는 이유는, 그러지 않으면 프롬프트를 고쳐도 캐시가 히트해 옛 결과가
계속 나오기 때문이다.

## 11. 보안

- **모든 API가 인증 없이 열려 있다.** 조회뿐 아니라 **상태를 바꾸는 API도 인증이 없다** — 감시 법령 삭제, 전문 삭제, `/api/config`를 통한 API 키 변경까지 누구나 호출할 수 있다. 기본 바인딩이 `127.0.0.1`이라는 전제에 기대고 있는 구조다.
- **외부에 공개하려면 앞단에 인증을 반드시 둔다.** 리버스 프록시(Nginx 등)의 basic auth로도 충분하지만, 없이 열면 키가 바뀌고 데이터가 지워질 수 있다.
- `/api/config`는 키를 **뒤 4자만 남기고 마스킹**해서 내려보내고, 저장 시 `config.json`을 `0600`으로 조인다.
- 문서 업로드는 20MB로 제한된다. 업로드 파일은 임시 파일에 쓰였다가 검사 후 삭제된다.
- **`config.json`에 API 키·비밀번호가 평문 저장된다.** 외부 공유·형상관리 커밋 금지. 환경변수 방식(2번 참고)을 권장한다.
- 법제처 API는 HTTPS로 호출한다.
- 리포트 CSV의 수식 인젝션(`=`, `+`, `-`, `@`)을 자동 차단한다.
- DB는 전용 계정 사용을 권장한다(1번 참고).

## 12. AI 분석 비용

`llm.api_key`가 설정돼 있으면 **매일 자동 확인 후 실제 API를 호출한다.**

억제 장치는 두 가지다.

- `collect.max_analyze` — 1회 최대 건수 (기본 20)
- `content_hash` 캐시 — 조문이 그대로면 재분석하지 않음

비용을 완전히 없애려면 `llm.enabled`를 `false`로 둔다. 이 경우 규칙 기반 판정으로 대체되며, 결과의 `engine`이 `rule`로 기록되고 신뢰도는 "하"로 표시된다.

## 13. 다른 환경으로 옮길 때

| 항목 | 교체 방법 |
|---|---|
| **LLM** | `llm.base_url`에 Qwen 등 OpenAI 호환 서버 주소. 코드 수정 불필요 |
| **프론트** | 순수 HTML/JS. Node·npm 불필요, 파일 복사만으로 이전 |
| **DB** | 아래 참고 — `_exec`/`_fetch` 교체만으로는 부족하다 |

DB를 Oracle·Tibero 등으로 또 옮길 때 손볼 곳. (MySQL → PostgreSQL 이관에서
실제로 걸렸던 것들이라 목록이 구체적이다)

- `Store._exec` / `_fetch` / `_exec_many` / `_schema` / `_ensure_columns`
- **파라미터 표기** — 질의문은 `%s`로 쓰고 `_to_pg()`가 실행 직전에 `$1`로 바꾼다.
  Oracle이면 `:1`로 바꾸는 함수만 갈아 끼우면 된다
- **`ON CONFLICT` 7곳** — Oracle은 `MERGE`다
- **인덱스 선언 위치** — PostgreSQL은 `CREATE TABLE` 안에 인덱스를 못 넣어
  `CREATE INDEX`로 분리했다. MySQL은 인라인이었다
- **타입 자동 변환 없음** — asyncpg는 DATE 컬럼에 문자열을 거부한다.
  aiomysql이 알아서 바꿔 주던 부분이라 `_as_date()`가 `date` 객체를 돌려주도록
  고쳐야 했다. 이관에서 가장 조용히 깨지는 지점이다
- **`LIKE` 대소문자** — MySQL 기본 콜레이션은 안 가리고 PostgreSQL은 가린다.
  검색 2곳을 `ILIKE`로 바꿔 기존 동작을 유지했다

## 14. 알려진 제약

- 법제처에 등록되지 않은 명칭은 `검색안됨`으로 남는다. 폐지·통합된 규칙이 여기 해당한다.
- **비교할 이전 판본이 없는 개정**(법령을 수집한 직후 첫 개정)은 전문을 그대로 분석한다.
  조문 특정 정확도가 떨어지므로 화면과 리포트에 `비교 대상 없음`으로 표시된다.
- **판본은 지금부터 쌓인다.** 처음 수집한 법령은 판본이 하나뿐이라 판본 비교에 비교 대상이
  없고, 전문 목록의 변경 배지도 `-`다. 개정이 감지될 때마다 채워진다.
- 전문 텍스트(`law_fulltext.content`)에는 **부칙을 최신 3건까지만** 넣는다. 다만 판본별 부칙은
  `law_addenda`에 제한 없이 누적되므로, 분석과 화면은 그쪽을 쓴다.
- **문서 검사**는 인용 법령의 *이름*이 현행인지만 본다. 조문 번호가 실제로 존재하는지,
  인용한 내용이 현행 조문과 맞는지는 대조하지 않는다.
- 문서 검사의 `개명 의심`은 개명과 약칭을 구분하지 못한다. `core.py`의 `SEARCH_ALIAS`가 개명·
  약칭·띄어쓰기 보정을 한 표에 담고 있어서다. 약칭 인용(`사회보장급여법` 등)도 걸린다.
- hwp/pdf/docx를 읽으려면 별도 패키지가 필요하다(1번 참고). 없으면 `.txt`만 처리된다.
